# 牛腰带 PCB32

奶牛围产期可穿戴监测腰带（PCB32 版本）。

## 研究定位与边界

### 已确认事实

本项目的研究主目标是实现奶牛围产期疾病预警系统，但不保证一定成功。如果目标牛场的病牛样本不足，或者现有数据无法支撑疾病预警，就需要转向备选研究问题；节律研究只是可能方向之一，当前备选路线尚未确定。行为识别是服务于预警的中间能力，不是最终研究目的。

腰带与项圈的主体监测功能相同；腰带相比项圈只多一个气囊，用于呼吸测量。

### 传感器与部件职责（已确认）

| 部件 | 直接职责 |
| --- | --- |
| QMI8658A | 提供运动数据，为行为识别提供输入 |
| GZP | 测量气囊压力变化，目标是获取呼吸信息 |
| ICP-20100 | 辅助识别起卧 |
| MTS4 | 测量体表温度 |
| SD | 保存正式传感器数据 |
| NF-03 | 只发送低频心跳，不发送传感器数据；心跳用于证明设备仍正常工作并提供时间对齐锚点；在满足这两个目的的前提下，发送频率应尽可能低以节省功耗 |
| OLED | 仅用于首次启动后的短时自检，之后不参与正式运行 |

设备的预期生命周期是：首次启动完成自检后进入休眠，等待外部信号唤醒；唤醒后持续采集数据、记录数据并发送低频心跳；此后设备再次重启时不应重新进入首次休眠状态。这里记录的是设计意图，不声称当前固件已经实现上述全部生命周期或时间对齐设计。

牛场短时录像及可能进行的一周试戴属于预实验，用于确认佩戴、对时、连续记录和信号可用性，不是正式疾病预警有效性证据。

### 尚待讨论

以下事项尚未形成既定方案：变量构造、数据基本单位与时间语义、建模方法、具体疾病预警方法、备选研究路线、外部唤醒实现，以及 NF 与 SD/录像的具体对齐实现。

- 主控：STM32G030K8T6 (ARM Cortex-M0+)

- 气压：ICP-20100、GZP 系列
- 温度：MTS4
- 无线：NF-03（2.4 GHz）

## NF-04 心跳与电脑监控

固件在传感器、SD 卡和日志创建完成后立即发送一次启动心跳（seq=0），随后
按运行时绝对 30 分钟网格发送（seq=1、2……），不会从每次发送完成后重新计时。
正式心跳周期固定为 `1800000 ms`（30 分钟）。真机首包和第二包验证、功耗测试
均直接使用这一套正式固件。

NF-04 心跳固定 32 字节，协议版本为 3，字段为：

| 字节 | 含义 |
| --- | --- |
| 0–2 | 构建/部署时配置的设备 ID（大端字节序显示） |
| 3 | 协议版本（V3） |
| 4 | 消息类型（1：心跳） |
| 5–8 | 心跳序号（大端 uint32） |
| 9–12 | 设备单调运行时间 ms（大端 uint32） |
| 13–16 | QMI、ICP、GZP、MTS4 状态 |
| 17 | SD 初始化成功 bit0、正在记录 bit1、SD 已满 bit2 |
| 18–31 | 保留，发送为 0 |

每个 30 分钟逻辑心跳使用同一序号发送三份单向广播：首份立即发送，后两份在
5–15 秒和 15–30 秒窗口内按设备 ID、序号和副本序号确定性分散。每份发送前
重新组装实际运行时间与传感器/SD 状态；不启用自动 ACK 或自动重试。MicroPython
与 Arduino 接收端都监听共同 RF 地址，并把每一份通过协议校验的物理报文逐条输出为稳定的
`NF04_HEARTBEAT {JSON}` 或 `NF04_ERROR {JSON}` 行。电脑端面板启动后可刷新并选择
接收端串口；也可以直接用 `--port` 预选，再运行：

```bash
python3 工具/nf04_monitor.py
# 高级用法：预选串口
python3 工具/nf04_monitor.py --port /dev/ttyACM0 --csv nf04-heartbeats.csv
```

面板按物理接收记录逐行显示在线/超时、电脑接收时间、序号、设备运行时间、四类
传感器状态和 SD/记录状态；同一设备同一序号的三份广播会各占一行，不会覆盖旧记录。
CSV 为每一份通过协议校验的心跳追加一行，并包含 `duplicate` 标记；它不是去重后的
逻辑摘要。面板还在 CSV 同目录追加保存 `nf04-monitor.log` JSONL：每一份实际报文
按电脑接收顺序写入一个 `heartbeat_raw` 事件，完整保留接收时间、设备 ID、协议版本/类型、
序号、运行时间、全部传感器状态、SD 初始化/记录活动/已满状态和 `duplicate: true/false`。
重复标记只用于说明副本关系和序号/统计诊断，不会丢弃、缩减、覆盖或改写任何原始接收记录。
面板中的“清空显示”只清除当前列表和错误提示，不删除、截断或覆盖 CSV/JSONL，清空后仍会
继续接收追加。面板重启或重新连接会继续使用同一文件；这些本机运行输出由 `.gitignore` 排除。
默认超时阈值为 32 分钟；可以用 `--timeout-seconds` 集中调整。未知协议版本、
损坏 JSON、串口断开均显示为错误，不会让面板退出。

启动首包和绝对周期推进由 `固件/源码/issue3_logic.h` 的共享 C 状态机定义，
固件与 `工具/test_issue3_logic.c` 直接复用；电脑端测试只验证协议、记录时间和
面板状态，不复制固件调度算法。

长期集成测试分开报告 SD 时序：正常成功读写模型（5 ms/5 ms）运行 4 小时，
GZP 原始计划 144000 次全部启动并读取，二分后 72000 个结果落盘，真实漏采为 0；
声明的 SD 读/写上界（29 ms/13 ms）
是故障压力边界，不是“采样通过”场景，测试会明确显示其真实漏采数量、重复数和
时间顺序，并验证漏采被计数且采集不会永久停滞。该压力结果不能替代真实 SD 卡长测。

正式采集期间，SD 的读响应/token、512 字节数据块、写响应和 busy 等待使用固件与
主机测试共用的可暂停状态机。SD 与 NF 共用 STM32G030 的 SPI1（PA5/PA6/PA7，AF0）：
SD 识别阶段使用 HSI16/PCLK÷64=250 kHz，完成首个扇区探测后切换到 PCLK÷8=2 MHz；
两条路径均由同一总线所有权和独立 CS 保护。每次最多推进 8 字节，硬件线上 4 us/字节，
连同寄存器轮询和 CS 开销按 8 us/字节设有界上限（单步最多 64 us）。步骤之间先服务
GZP、QMI 和 ICP；启动探测与日志创建发生在正式采集开始前，仍可使用同步初始化路径。
常规 120 ms 扇区写入场景因此要求 GZP 计划、启动、落盘逐点一致且 `missed=0`；
新的 29/13 ms SD 读/写声明上界只作为单独的不可承受压力诊断。
帧保留窗口仍额外保留 1.82 s 的卡内部 busy/元数据安全余量；这不是把旧软件
SPI 吞吐当作新的性能结论。
GZP 转换完成结果使用固定上限的共享小队列跨越短暂 SD/FAT 占用，结果满时才按
实际无法承受的计划网格计为漏采，不通过放宽迟到容限掩盖损失。

正式 BIN 日志当前为 V4：每秒帧大小 368 字节（CRC 位于偏移 364），QMI 槽位 16、
GZP 槽位 5、ICP 槽位 2、MTS4 槽位 1。QMI 仍以约 28.025 Hz 读取并推进原生 FIFO
时钟，GZP 仍按 100 ms 绝对计划网格转换和读取；二者只在成功读取之后由跨 FIFO/转换、
跨帧持久相位各保留连续两个原始项目中的一个；迟到仍在容限内时保留原网格时间，
超出迟到容限而启动当前转换时使用实际启动时间戳。
有意二分不计为 missed、drop、late 或 overflow；真实 I²C、转换、FIFO、队列和时间
窗口故障仍按原诊断报告。`工具/bin2csv.py` 同时保留 V1/V2/V3 历史日志解析。

QMI 运行期的停滞看门狗以“最后一次成功读取完整原始样本”的单调运行时间为唯一期限
基准，而不是只等待某一种 FIFO 状态：初始化后尚未成功读到第一批，或之后连续 500 ms
没有成功原始样本，且 100 ms QMI 服务仍在运行，就触发一次有界恢复。合法空 FIFO、
count/`FIFO_STATUS` 矛盾、非空 FIFO 的 CTRL9/FIFO_DATA/cleanup 失败都会留在这条
无成功样本计时路径；单次瞬态错误不会立即重复重置。恢复退出读模式、RST_FIFO、重写并
读回当前 CTRL1/2/3/6/7/8、水位和 FIFO_CTRL，再独立读回 count LSB/status，核验 count=0、
`NOT_EMPTY/WTM/FULL/OVERFLOW` 全部清零及 `FIFO_RD_MODE=0`，失败后至少 1 s 才重试。
每次停滞恢复尝试写入 V4 状态位 10（兼容旧名称 `qmi_empty_recovery`），成功/失败分别
按事件累计 OR 写入位 11/12；无论寄存器恢复成败，旧 QMI 时钟都会失效，下一批成功原始
样本按当前时间重新锚定。`bin2csv.py` 输出这三个可读状态列，历史 V1/V2/V3 帧按零值
兼容解析。

即使 FIFO_DATA 每次都成功，运行期每个合法非空批次仍会用
`batch_now_us - (samples - 1) * ISSUE3_QMI_SAMPLE_PERIOD_US` 计算当前采样窗口；若旧软件
时钟落后该窗口超过 500 ms，则在读取样本前前移重锚并保留 `qmi_reanchors`/重新锚定状态。
小于该阈值的 100 ms 调度抖动继续沿用原时钟，不会每批重锚；批次锚点保证最后一个样本时间
不晚于本次读取时刻且输出时间单调。该校正独立于“500 ms 无成功原始样本”恢复看门狗。

QMI 的正式 FIFO 服务在确认有合法完整样本后直接进入读模式，逐个读取整个批次；某个
保留样本若落到 TIME、SD-owned OWNER 或 QUEUE 阻塞，只丢弃并记录该样本，不能拒绝
同批次后续样本，也不会因此复位 FIFO 或重新锚定。GZP 服务轻微迟到时仍启动当前网格
点；若已经越过多个网格，则只把已经完整错过的历史点计为 missed，最多启动一个当前
转换，并在超过迟到容限时用实际启动时间作为结果时间戳，下一截止点仍回到未来的绝对
100 ms 网格，不背靠背补做历史转换。

### 实机 SD 瓶颈定位诊断（本轮新增）

正式固件包含一个只驻留 RAM、不会写入 SD 或发送到 NF 的诊断区：
`volatile Issue3RuntimeDiagnostics r_issue3_diag`。正式运行开始后其首字段应为
`magic=0x49534433`、`version=1`；启动探测不会混入计数。结构记录主循环和
`sd_async_step()` 进度、同一活动事务内相邻 step 的最大间隔、扇区完成间隔、持久化字节和完整帧数、帧队列与
GZP 结果队列峰值、QMI/GZP/ICP 接收与入帧数，以及按队列/时间窗口/物理槽所有权
分类的丢弃数。

`sd_step_max_gap_ms` 只在同一尚未结束的 SD 事务中比较相邻两次
`sd_async_step()`；事务完成后会清除活动身份，因此两个独立事务之间的正常空闲不会
污染该字段。事务、step、阶段、扇区完成、FAT 预取/簇链接/metadata 和 TIME/OWNER/QUEUE
丢弃分类均通过 `固件/源码/issue3_logic.h` 的共享状态入口更新，主机诊断测试与正式
`main.c` 使用同一转换逻辑。

帧丢弃分类来自实际 frame-open 结果：TIME 表示时间戳早于可恢复窗口或落入不可恢复
时间孔洞，OWNER 仅表示该时间戳实际命中的物理槽由 SD pending 持有，QUEUE 表示需要
新开/补开帧但容量或其他队列条件阻塞；不会再以“存在任意 pending 槽”推断 OWNER。

SD 部分包括读/写/总事务数、每个完整事务的最近/累计/最大耗时、SPI 传输字节、
read-token 与 write-busy 轮询总数和单事务最大值、SPI 超时次数。`sd_transaction`
及 `sd_phase[0..6]` 的元素均为 `{entries,total_ms,last_ms,max_ms}`；阶段索引为：
`0 CMD`、`1 响应`、`2 读 token/写 token`、`3 读数据/读 CRC`、`4 写数据/写 CRC`、
`5 写响应`、`6 write-busy`。`total_ms` 为饱和的 32 位累计值，单次 `last_ms`/`max_ms`
为饱和的 16 位毫秒值（超过 65535 ms 会保留为 0xffff）。`fat_prefetch`、
`fat_link`、`metadata` 使用相同的四字段结构，分别对应 FAT 预取/分配、簇链接和
目录元数据逻辑操作。

Tiger 可在运行约两分钟后通过 ST-Link/GDB 一次读取完整结构（端口按现场 OpenOCD
配置替换）：

```text
arm-none-eabi-gdb 固件/编译输出/firmware.elf
(gdb) target extended-remote :4242
(gdb) monitor halt
(gdb) set print pretty on
(gdb) p/x r_issue3_diag
```

本诊断提交只用于区分 SPI 传输、卡 token/busy、FAT/元数据和前台推进间隔造成的
瓶颈，不表示吞吐问题已经修复；读取后请保留 magic/version 及全部字段原样记录。

正式主循环不会在每个 8 字节步骤后无条件执行 WFI：只要 SD/FAT、FIFO、待提交帧或
转换结果有可立即推进的工作，就继续服务传感器并推进下一步。QMI 保留 PB6/EXTI
快速路径，同时由 TIM3 每 100 ms 置独立的 FIFO/status 轮询标志；即使水位边沿漏掉，
仍会读取真实 FIFO level/status 并复用完整批次逐样本读取、溢出恢复和重新锚定逻辑。ICP 没有
中断线，由另一个独立的 100 ms 标志限频服务；SD 每个 8 字节步骤前先服务 QMI，再
服务到期 ICP，I²C 失败由下一轮继续重试，不把传感器停采变成前台忙轮询。GZP 约
20 ms、MTS4 约 50 ms 的转换完成期限使用 TIM3 比较唤醒；100 ms 更新中断负责较长期限，因此
WFI 不会把短转换拖到下一个 100 ms。日志还以完整数据扇区的实际完成时间作为进度
心跳；超过一个帧保留窗口加 5 秒仍有待写入工作却没有进度时，`log_active` 会清零，
避免心跳继续把写入停滞报告为正常记录。

主循环睡眠入口使用 `issue3_runtime_sleep_entry()`：先在关中断（PRIMASK）状态下重新
读取全部前台工作、软件到期标志和 TIM3/QMI 硬件 pending 位，再配置比较唤醒，执行
DSB/WFI，最后恢复中断。NF 的运行期短等待另使用同语义的
`issue3_atomic_wait_begin()`/`issue3_atomic_wait_step()`：新等待在同一关中断区内
关闭旧 CC1IE、清除上一轮 CC1IF、清零完成标志、读取 CNT、设置新的 CCR1 并启用
CC1IE；若配置期间计数跨过目标，则从新 CNT 重新建立目标。随后再在关中断后检查
`r_short_timer_done` 和 TIM3 pending，因此旧 pending 不会替代本次延迟，新事件仍会
保持 pending 并唤醒 WFI。Cortex-M0+ 在 PRIMASK 期间到达的 TIM3 比较、TIM3 更新或
QMI EXTI 会保持 pending 并唤醒 WFI，随后由 ISR 处理；比较配置不会清除刚到达的
pending 标志。`工具/test_issue3_logic.c` 和四小时异步测试直接调用共享入口，覆盖主
循环三种竞态、旧 CC1IF、计数回绕和配置前进，避免用独立的理想睡眠模型替代固件路径。

异步生产路径的四小时离散事件回归位于
`工具/test_issue3_async_long_capture.c`。它直接驱动 `Issue3SdTransfer`、
`Issue3SpiBus`、帧队列、QMI 逐样本 FIFO 服务、GZP/ICP 调度和 `Issue3LogPrefetch`，模拟
约 28.025 Hz QMI 原始读取、10 Hz GZP 原始转换、2 Hz ICP、30 分钟 MTS4、QMI EXTI 永不触发时的
100 ms 轮询兜底、ICP 100 ms 限频服务和非零 I²C 时间成本、V4 368 字节帧跨扇区和 FAT
跨簇链。运行期簇分配和旧簇到新簇的链接也逐步通过异步 FAT0/FAT1 扇区读写完成；
同步 FAT 访问只用于启动初始化和结束时的测试清理。SD 命令、token、数据和 busy
阶段之间继续推进传感器与 NF。测试以离散时间
运行四小时而不是等待现实四小时，最后从模拟卡的目录有效长度、FAT0/FAT1 链和实际
扇区字节反解析帧、CRC、样本唯一性和三副本心跳。主机上可用以下命令运行：

```bash
cc -std=c11 -O2 -Wall -Wextra -Werror -I固件/源码 \
  工具/test_issue3_async_long_capture.c -o /tmp/test_issue3_async_long_capture
/tmp/test_issue3_async_long_capture
```

NF-03 与 SD 共用硬件 SPI1 线，运行期由共用 C 所有权状态机互斥：SD 从命令开始直到
响应、数据、busy 完成并释放 CS 前，NF 只保留待发送副本，不访问 SPI；NF 发送、唤醒
和休眠期间也不会启动新的 SD 事务。心跳副本在总线释放后继续使用原序号和实际发送时刻
重新组包。主机回归覆盖 SD 命令、读 token、写数据和写 busy 阶段的到期心跳，并检查两
个 CS 从不同时有效。正常 120 ms 分步 SD 集成还持续产生 ICP 2 Hz 样本，样本经过 FIFO、
帧队列和模拟 SD 字节后按时间戳反解析，要求输入与落盘一一对应、无重复和漏采。
