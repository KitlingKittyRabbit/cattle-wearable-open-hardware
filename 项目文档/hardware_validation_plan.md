# PCB32 真机验证计划

## 1. 目的与范围

本计划用于验证当前 STM32G030K8T6 固件在已经完成基础 bring-up 的 PCB32 硬件上的回归行为。重点是确认固件修改没有破坏原有的启动、传感器采集、SD 存储、NF-03 通信和 Reset 恢复流程。

本计划不重复短路检查、器件方向检查、限流上电、焊接检查等新板首次 bring-up 项目，也不覆盖功耗、续航和低功耗待机。

当前可用测试条件：可烧录和 Reset，有 OLED 和 SD 卡；有 NF-03 接收端时可做真实无线收包；有普通万用表；不依赖示波器或逻辑分析仪。

## 2. 测试前记录

开始测试前，先复制 `项目文档/硬件验证/TEMPLATE.md`，按命名规则保存为：

```text
项目文档/硬件验证/<嘉立创订单编号>_<YYYYMMDD>.md
```

记录以下信息：

- 嘉立创订单编号。无法区分同一订单中的单板时，不虚构板号。
- PCB revision / 硬件版本；没有明确标识时填写 `未知`。
- 固件 Git commit SHA。
- 测试日期和操作者。
- 供电方式、电池或外部电源信息。
- SD 卡容量、品牌和文件系统信息。
- NF-03 接收端是否可用。

测试前确认固件构建成功，并将实际烧录的 commit SHA 填入记录。测试过程中的每个项目必须填写 `PASS`、`FAIL` 或 `NOT TESTED`，并记录观察到的数值和现象。

## 3. 启动流程

1. 烧录待验证固件并 Reset 或重新上电。
2. 观察 OLED 启动自检，记录 QMI8658A、GZP、ICP-20100、MTS4、SD、NF-03 的状态和显示值。
3. 确认自检有结束点，不会永久停留在启动测试界面。
4. 确认设备无需人工操作即可进入正常采集流程。
5. 确认有 SD 卡时进入存储流程，有 NF-03 初始化成功时进入发送流程。

判定：各模块状态可观察、自检结束并进入正常工作流程为 `PASS`。自检永久阻塞、关键状态无法显示或设备未进入采集/存储/发送流程为 `FAIL`。

说明：`OK/FAIL` 只表示固件是否完成有效读取或初始化，不自动判定测量值的物理正确性。传感器数值是否合理由现场观察记录单独判断。

## 4. 传感器回归

### 4.1 QMI8658A

1. 设备进入正常采集后，记录 OLED 上的三轴加速度和三轴陀螺仪读数。
2. 静止观察一段时间，再移动和旋转 PCB。
3. 记录读数是否持续更新，以及动作是否引起可重复观察的变化。

读数持续存在且移动、旋转与读数变化有可观察关联为 `PASS`。读数缺失、长期不变、明显异常或动作与读数无关联为 `FAIL`。

### 4.2 GZP

1. 连接实际使用的气囊。
2. 压缩并释放气囊多次。
3. 记录 OLED 上的压力读数和变化方向、幅度等现象。

压力读数持续存在，并对压缩和释放产生明显对应变化为 `PASS`；否则为 `FAIL`。

### 4.3 ICP-20100

1. 记录持续压力和温度读数。
2. 在条件允许时改变高度或施加明显压力变化。
3. 记录读数是否出现相应变化。

能够持续取得读数，且动作与读数存在可观察关联为 `PASS`；否则为 `FAIL`。

### 4.4 MTS4

1. 记录静置时温度读数。
2. 用手接触或捂热传感器一段时间。
3. 松开后继续观察，记录温度变化。

读数处于现场认为合理的范围，并对接触或捂热产生可观察变化为 `PASS`；否则为 `FAIL`。

## 5. SD 卡

### 5.1 SD 持续存储

1. 正式采集开始后确认 SD 卡产生新的记录文件。
2. 运行一段时间后再次确认文件大小或记录内容持续增长。

只要记录文件产生并持续增长，SD 持续存储即为 `PASS`；没有新记录、只写入一次后停止或写入失败为 `FAIL`。未执行该项时填写 `NOT TESTED`。

### 5.2 SD 数据解析

1. 停止测试后取出 SD 卡，取得一小段实际产生的数据。
2. 使用仓库现有 `工具/bin2csv.py` 尝试解析该样本。
3. 将足以证明解析链路正常的小型样本保存到 `项目文档/硬件验证/证据/`，不要提交长时间实验产生的原始数据。

小型样本由当前解析工具正确解析为 `PASS`；样本无法解析或解析结果不正确为 `FAIL`；未执行该项时填写 `NOT TESTED`。该结果只评价主机端解析链路，不反向改变 SD 持续存储结果。SD 文件正常产生并持续增长、但解析失败时，应记录 SD 持续存储为 `PASS`、SD 数据解析为 `FAIL`，并在异常中记录解析失败现象。

## 6. NF-03

### 6.1 开机本地自检

记录 OLED 上 NF-03 的启动状态。该项只确认 STM32 与 NF-03 之间的 SPI 寄存器读写和初始化，不依赖外部接收端。

本地寄存器读写和初始化成功为 `PASS`，失败为 `FAIL`。

### 6.2 真实无线收包

有可用接收端时：

1. 启动接收端并记录接收端程序、配置和开始时间。
2. 让腰带运行正常采集和发送流程。
3. 确认接收端收到预期测试数据，并记录数据包数量、时间范围或关键字段。
4. 将小型接收日志保存到 `项目文档/硬件验证/证据/`。

收到了预期数据为 `PASS`；已执行但没有收到预期数据为 `FAIL`。

没有接收端时，真实无线收包项填写 `NOT TESTED`，不能用开机自检结果替代真实链路验证。

## 7. Reset 回归

1. 设备进入正常采集后手动 Reset 多次，建议至少记录 3 次；实际次数填写在验证记录中。
2. 每次观察启动自检、自检结束、采集恢复、SD 恢复和 NF-03 恢复情况。
3. 记录任何偶发启动失败、外设不恢复或传感器状态异常。

每次 Reset 后都能完成启动并恢复正常采集、存储和发送流程为 `PASS`。任一次失败都将该项判为 `FAIL`，并记录失败次数和现象；未执行则为 `NOT TESTED`。

## 8. 结果与证据留档

每次测试保存一份记录到 `项目文档/硬件验证/`，使用 `TEMPLATE.md` 的字段。记录必须包含：

- 每个项目的 `PASS` / `FAIL` / `NOT TESTED`。
- 关键实际观察值和现象。
- 异常、偶发问题和未完成项目。
- 小型 SD 样本、NF 接收日志或其他证据的仓库路径。

长期实验原始数据、完整 SD 卡导出和过大的无线日志不提交到 Git。小型、脱敏、可复现检查所需的证据可以放在 `项目文档/硬件验证/证据/`，并在记录中注明用途。

## 9. Acceptance Criteria 对照

本计划完成以下 Issue #4 要求：

- 提供一套明确、可重复执行的真机回归验证步骤。
- 测试条件与当前设备一致，不要求示波器或逻辑分析仪。
- 明确这是已有硬件上的固件回归，不重复新板基础 bring-up。
- 覆盖启动、QMI8658A、GZP、ICP-20100、MTS4、SD、NF-03 和 Reset 回归。
- 每个项目均使用 `PASS`、`FAIL` 或 `NOT TESTED`，并记录实际观察值和现象。
- 使用嘉立创订单编号作为 PCB/SMT 批次追溯标识；无法区分同一订单中的单板时不虚构板号。
- 提供 `项目文档/硬件验证/TEMPLATE.md` 作为验证记录模板。
- 预留 `项目文档/硬件验证/证据/` 保存小型 SD 样本和 NF 接收日志；长期原始数据不提交。
- 将功耗、续航和低功耗待机明确排除在本计划之外。

仓库中的验证计划和模板不代表任何一次真机测试已经完成。首份实际记录必须在人工烧录、操作和观察硬件后填写；在此之前不得将任何项目填写为已验证的 `PASS`。
